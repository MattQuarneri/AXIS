AXIS: Agentically eXtensible Instruction Structures

The Essence–Expression Meta-Architecture — A cognitive and structural model for organizing software according to how intent becomes behavior and behavior produces change.

Why AXIS Exists: A Meta-Architecture for Codified Logic Foundational Thesis

Most successful architectural styles—Clean Architecture, Domain-Driven Design, CQRS, Event Sourcing, MVC, Flux/Redux—have independently discovered the same useful patterns: pure business logic, explicit boundaries, immutable state, and event-driven workflows.

AXIS is not a replacement for those patterns. It is the underlying cognitive vocabulary that explains why they work and unifies them into composable, testable seams for both human engineers and synthetic coding agents.

Immutable Essence (Static)

Defines what something is: generative shapes, enduring identity, capability maps, relationship rules, pure logic, and declared effects.

Projected Expression (Dynamic)

Defines how it manifests at runtime: live state snapshots, scoped tokens, intents, graph hydration, orchestration, and IO execution.

AXIS-Principles.md · Foundational Premise

The Cognitive Flow of Change

Software exists to produce change. Change is not produced directly—it emerges from behavior, which executes instructions refined from progressively higher levels of intent.

← Expresses Purpose & Meaning (Why) Click any stage to inspect its architectural mapping Expresses Runtime Execution (How) →
Why This Progression Matters Architectural Axiom
  • Downward Constraint: Each layer constrains and gives meaning to the layers beneath it.
  • Technology Independence: Architecture should not be organized around transport protocols, frameworks, or persistence engines.
  • Semantic Traceability: When an agent or engineer inspects an Action or Effect, its lineage back to an Intent, Facet, and Form invariant is explicit in code.
  • Closing the Loop: Dynamic behavior produces Change, and committed Change becomes the new declarative Instance state for the next cycle.
AXIS-Principles.md · Orthogonal Decomposition

The Essence–Expression Principle

Every architectural concern has a Static Essence (being, definition, contract) and a Dynamic Expression (doing, projection, runtime realization).

Immutable Essence — "What Something Is" Static · Generative · Pure

Essence consists of stable definitions, identities, capability surfaces, relationship rules, pure transformations, and causal descriptions.

  • FORM: Generative schema, defaults, and invariants (holds no live values).
  • IDENTITY: Immutable sameness and addressing policy across time.
  • FACET: Static capability map associating capability keys with Action delegates.
  • BOND: Declarative relationship topology, ownership, and cross-entity invariants.
  • ACTION: Pure, deterministic function (state, intent) → { delta, effects[] }.
  • EFFECT: Pure data value describing a desired side effect (never self-executing).
  • WRAPPER: Structural boundary (DOM root, Shadow DOM, HTTP server socket).
Projected Expression — "How It Manifests at Runtime" Dynamic · Temporal · Contextual

Expression consists of materialized state snapshots, scoped tokens, active interpretations, graph traversal, orchestration, and side-effect execution.

  • INSTANCE: Materialized, versioned state snapshot (all mutable state lives here).
  • TOKEN: Scoped, expirable, revocable temporal projection of Identity with claims.
  • INTENT: Normalized, replayable semantic artifact ("what someone meant to do").
  • LINK: Runtime traversal and graph hydration of a Bond within a query scope.
  • MANAGER: Boundary-scoped orchestrator (Composer + Conductor).
  • IMPACT: The sole site where IO, retries, and compensating rollbacks execute.
  • ADAPTER: Edge transformer normalizing raw events + raw auth into Intents.
The Generative Cycle of Essence & Expression Structural Loop
1. Static Structure Forms, Bonds, Facets, and Actions define what is valid and possible without executing IO.
2. Dynamic Behavior Adapters emit Intents; Managers route via Tokens & Facets to pure Actions.
3. Controlled Change Actions return { delta, effects[] }; Impact executes IO with retry & compensation.
4. New Declarative State Manager validates Form & Bond invariants and commits a new versioned Instance.
AXIS-Principles.md · Architectural Commandments

The 10 Principles of AXIS

The fourteen architectural components are not an arbitrary checklist—they are the natural consequences of these ten principles.

01. Organize around behavior, not technology Structure

Structure software according to responsibilities and behavior rather than frameworks, transport protocols, or persistence mechanisms.

02. Follow the Cognitive Flow of Change Cognition

Higher levels of intent (Values → Goals → Plans → Declaratives) progressively refine into executable instructions, actions, and change.

03. Separate Essence from Expression Duality

Explicitly separate definitions from execution (`Form` vs. `Instance`), enduring identity from temporal scope (`Identity` vs. `Token`), and declarations from realization (`Effect` vs. `Impact`).

04. Treat behavior as the engine of change Dynamics

State never mutates spontaneously or ambiently; behavior (`Action` transformations committed by a `Manager`) is the sole engine that transforms state.

05. Treat side effects as data until execution Testability

Describe change before performing it. `Action`s return pure `Effect` descriptors; only `Impact` touches the outside world.

06. Treat responsibility as a routing problem Policy

Every behavior has an explicit owner and execution path: `Intent` + `Token` claims route through a `Facet` capability map to an `Action` delegate.

07. Prefer composition over inheritance Modularity

Assemble systems from composable capability overlays (`Facet`s), action pipelines, and relational `Bond`s rather than deep class hierarchies.

08. Design explicit boundaries Encapsulation

Every component owns one responsibility with a strict contract. `Manager`s own a single consistency boundary and communicate across contexts only via `Effect`s.

09. Dependencies are supplied, not discovered Purity

Components receive pre-hydrated state (`Instance` + `Link` graph) and `Intent` payloads rather than reaching out to global singletons or service locators.

10. Form follows responsibility Clarity

Codebase topology should immediately reveal what the system does and where state, policy, and IO live—for both humans and machine agents.

AXIS-Design.md & AXIS-Lite.md · Orchestration Discipline

Inside the Manager: Composer, Conductor & Bounded Contexts

A Manager is a boundary-scoped coordinator, never a catch-all service class. It owns one consistency boundary, one commit path, and one policy surface.

1. The Composer (Setup-Time Structure) manager/composer.*

Decides what is possible. Wires Adapters to Wrappers, registers Facets and Bonds, and installs Impact handlers. Runs at startup or when system structure dynamically changes (e.g., plugin/service registration). 

// Composer API (Structure)
manager.bind(wrapper)
manager.registerFacet(facet)
manager.registerBond(bond)
💡 Diagnostic: Composer growing complex? Add more Facets, not more wiring conditionals.
2. The Conductor (Runtime Performance) manager/conductor.* + commit.* + policy.*

Decides what happens now. Resolves Tokens, selects Facets, hydrates Links, invokes pure Actions, validates Form & Bond invariants on commit, and hands declared Effects to Impact. 

// Conductor API (Performance)
manager.dispatch(intent)
manager.commit(delta) → Instance // validates Form & Bond invariants
manager.issueToken(identity, scope, rawAuth) → Token
manager.resolveLink(link) → Link
💡 Diagnostic: Conductor growing branchy? Extract a Workflow sub-component or split Facets.
Cross-Boundary Communication: Managers Never Call Each Other Directly Bounded Contexts 
[ Bounded Context A: Orders ]                     [ Bounded Context B: Billing ]
  Manager A (owns Order Instances)                  Manager B (owns Invoice Instances)
      ↓                                                 ↑
  Action → Effect { kind: "EMIT_EVENT" }            Adapter → Intent { kind: "order.placed" }
      ↓                                                 ↑

The 5-Part Manager Boundary Contract AXIS-Lite Interface
  • 1. Owned State: Which Forms, Instances, and Identities it may commit.
  • 2. Accepted Intents: Exact command/intent kinds it accepts.
  • 3. Emitted Effects: The only outward requests it can make.
  • 4. Returned Outcomes: Acknowledgements, rejections, and follow-ups.
  • 5. Policy Scope: Token claims and roles it is allowed to interpret.

Flux/Redux, CQRS, Event Sourcing & RBAC Natural Emergence
  • Flux / Redux: Replaces opaque Thunks/Middleware with pure EFFECT data + IMPACT handlers.
  • CQRS: Not a separate architecture—just a Write Facet vs. Read Facet selected by Token claims.
  • Event Sourcing: The Intent stream + committed deltas are the event log, surrounded by named validation (`Form`) and consequence (`Effect`) layers.
  • Roles & Capabilities: Token.claims (Who) → Manager (When/Where) → Facet.delegates (What) → Action (How).

6 Front-End Rules from AXIS-FrontEnd-Web.md Browser Discipline
  • 1. Wrappers Are UI Boundaries: Custom Elements / Shadow DOM own event slots and rendering slots, never business rules.
  • 2. Adapters Normalize Browser Noise: Convert raw DOM events, URL changes, or storage signals into replayable Intents (e.g. todo.toggle).
  • 3. Divs Are Projections, Not Domain Objects: Instance is the authoritative snapshot; the DOM is merely a visible projection.
  • 4. Actions Stay Pure: Never touch document, fetch, or localStorage inside an Action.
  • 5. Impact Owns Browser IO: DOM patches, stylesheet swaps, IndexedDB/localStorage, and network calls happen exclusively in Impact.
  • 6. Browser Token Families: Use GUID.name.value tokens (sessionToken, routeToken, viewToken, selectionToken) when runtime scope matters.

            Closing Synthesis · MENTIC Cognitive Systems
          

          
The 9 Core Mental Shifts & Architectural Takeaways

          

            AXIS does not begin with software components. It begins with cognition—asking how meaning becomes action, then deriving software structure from that progression.
          

        


        

          

            1. Events Express Intent
            
Events don't do work directly—Adapters normalize them into loggable, replayable Intent artifacts.

          

          

            2. Effects Are Data; Impact Is IO
            
Side effects have two distinct phases: pure declaration in Actions and runtime execution in Impact.

          

          

            3. Changes Are Values, Not Mutations
            
Actions compute delta values; only the Manager's Committer produces a new versioned Instance.

          

          

            4. Identity Is Permanent; Tokens Expire
            
Identity is timeless sameness; Tokens project identity into a specific session, scope, and claim set.

          

          

            5. Forms Generate; Instances Hold
            
Forms define shape, defaults, and invariants without behavior; Instances hold all live mutable state.

          

          

            6. Facets Are Capability Maps
            
Access control and lifecycle modes are data maps (capability → Action) selected by the Manager, not scattered if/else branches.

          

          

            7. Bonds Structure; Links Traverse
            
Bonds declare aggregate invariants externally; Links pre-hydrate entity graphs before pure Actions run.

          

          

            8. Composition Is Runtime Orchestration
            
Dynamic extensibility is simply committing a new Identity + Facet into a live Manager's Instance state.

          

          

            9. Failures Are Alternate Effects
            
Rejections, retries, and compensating rollbacks flow through the same testable data pipeline as happy paths.
