Meta-Architecture Cognitive Systems Design

Understanding AXIS

Software exists to produce change. Yet modern software architectures routinely drown in tangled state, leaky I/O, and blurred responsibilities. AXIS is not another framework—it is a cognitive map revealing how human intent becomes codified behavior, and how behavior safely produces change.

Act I · The Common Ground

Where We Begin: Classic Model-View-Controller

Every developer learns MVC. It gave the software industry its first clean vocabulary. So why does almost every production MVC project eventually degenerate into "fat models", "god controllers", and untestable spaghetti?

The Decompression Progression Watch how three overloaded buckets decompress into clean structural dimensions

In classic MVC, each of the three terms acts as an ontological landfill. Notice how many mutually contradictory responsibilities are stuffed inside each box:

MODEL Overloaded

Conflates static definitions with runtime snapshots:

  • Schema, types & field invariants Static
  • Relational parent/child rules Static
  • Live in-memory record state Dynamic
  • Session auth tickets & claim scopes Dynamic
  • Database queries & joins Dynamic
VIEW Overloaded

Conflates physical mount boundaries with projected facets:

  • Custom element & route shells Static
  • Render slots & event mount points Static
  • Visible role/lifecycle surfaces Dynamic
  • Theme / Layout visual facets Dynamic
  • Direct DOM mutations & listeners Dynamic
CONTROLLER Dangerous

Conflates pure math with irreversible side-effects:

  • Pure business calculations & logic Static
  • HTTP / DOM input normalization Dynamic
  • State commit & workflow orchestration Dynamic
  • Disk, SQL, Email, Fetch I/O Dynamic
💡 The Symptom: When a single class handles both a pure business calculation (e.g. discount logic) and a direct I/O call (e.g. database write or email send), unit testing requires heavy mocking, AI agents make catastrophic assumptions, and race conditions flourish.

Step 1 of AXIS: Separate Essence (Static Definition) from Expression (Dynamic Realization). Static structures define what something is; dynamic expression governs how it manifests at runtime.

ESSENCE (Static Definition)

The stable outline. Schemas, identities, pure functions, and capability maps. Contains no live values, no mutations, and no I/O.

Form (from Model): Schema, field types, invariant formulas
Identity (from Model): Enduring entity naming rule & ID policy
Bond (from Model): Static relationship rule, multiplicity, consistency constraints
Wrapper (from View): Structural shell, custom-element tag, host boundary
Facet (from View/Controller): Permitted capability lens (e.g. Draft vs Paid)
Action (from Controller): Pure deterministic transition function
Effect (from Controller): Declarative data description of requested side-effect
EXPRESSION (Dynamic Realization)

The runtime manifestation. State snapshots, scoped tokens, live orchestration, and concrete I/O. This is where time, lifecycles, and side-effects reside.

Instance (from Model): Committed in-memory state snapshot & revision counter
Token (from Model): Scoped session ticket, claim flags, expiration timestamp
Link (from Model): Pre-hydrated graph traversal and resolved entity pointer
Adapter (from View/Controller): Normalizes noisy browser/HTTP events into clean Intents
Intent (from Controller): Normalized command object describing user/system will
Manager (from Controller): Boundary coordinator, conductor, state committer
Impact (from Controller): Concrete executor that executes effects against the world

When you align each Static concept with its Dynamic partner, you discover Seven Orthogonal Cognitive Dimensions. Nothing is arbitrary: each row answers one fundamental question of computation.

          Act III · The Engine
          
How Change and State Operate

          

            Software does not mutate by magic. It transforms through a strict cognitive pipeline.
            AXIS's most powerful innovation is The Fork and The I/O Membrane.
          

        


        

          

            

              
1. The Purity Membrane

              

                In traditional code, functions perform HTTP requests, write to databases, or mutate DOM elements anywhere.
                In AXIS, a strict geometric boundary exists: The Membrane.
              

              

                Actions are strictly pure. They are mathematical formulas that take the current state and an Intent,
                and return what would change. Only Impact is allowed to penetrate the membrane and touch the outside world.
              

            

            

              
2. The Pure Fork: { delta, effects }

              

                When an Action executes, it emits two pure data structures:
              

              
    
                
  • delta: State modifications to be validated and committed to the Instance.
    • 
                
  • effects[]: Inert data objects describing what external work must happen.
    • 
              

              

                Neither has happened yet! If an invariant check fails on the delta, the transaction is rejected,
                and the effects are discarded without touching the database or sending duplicate emails.

          Act V · Pragmatism First
          
AXIS Lite: Preserving the Discipline, Not the Ceremony

          

            Do not let 14 terms overwhelm you. In 90% of real-world services and frontend components,
            you only need AXIS Lite. Add components only when the problem justifies it.
          

        


        
        

          
The 7 Non-Negotiable Hard Rules

          

            

              
1. Actions Stay Pure

              
They transform state and declare effects. They never call fetch, touch the database, or read system clocks.

            

            

              
2. Effects Are Data

              
An Effect is an inert JSON object describing what to do. It cannot execute itself.

            

            

              
3. Only Impact Performs I/O

              
Disk, network, queues, and DOM manipulation are quarantined strictly to Impact handlers.

            

            

              
4. Adapters Normalize at the Edge

              
Raw browser click events or HTTP payloads are sanitized into stable, replayable Intents immediately.

            

            

              
5. State Has One Explicit Owner

              
No loose global mutable variables. The Manager boundary owns and versions state transitions.

            

            

              
6. Invariants Validated on Commit

              
Every delta is verified against Form rules before state changes take effect. Invalid deltas are rejected cleanly.

            

            

              
7. Explicit Cross-Boundary Seams

              
Bounded contexts never touch each other's in-memory state directly. They communicate via declared Effects.

          Act VI · The Agentic Frontier
          
AI Coding Agents Need Maps, Not Just Prompts

          

            AI agents can generate syntactically correct code effortlessly. The hardest problem is structural:
            determining where logic belongs, what it is permitted to touch, and how to prevent architectural rot.
          

        


        

          

            

              ❌ The Prompt-Only Trap
            

            

              When an agent is asked to "add a discount feature" to a vague codebase:
            

            
    
              
  • It puts raw SQL/API calls directly inside an event handler.
    • 
              
  • It mutates shared global state without incrementing revision counters.
    • 
              
  • It misses cross-entity invariants.
    • 
              
  • It generates code that compiles, but damages the long-term maintainability of the project.
    • 
            

          


          

            

              ✅ The AXIS Placement Grammar
            

            

              With AXIS, the agent has an unambiguous decision tree:
            

            
    
              
  • Need to calculate? Implement a pure function in actions/.
    • 
              
  • Need external I/O? Declare an Effect, executed only in impacts/.
    • 
              
  • Need input mapping? Normalize it in adapters/.
    • 
              
  • Unit testing? Run the Action with input state. No database mocks, no network stubs required!
    • 
            

          

        


        

          
Harvesting Reusable Organs with Recomposition

          

            Code reuse should not start by copying files. It starts with identifying the functional closure
            around a capability. In AXIS, a capability's nucleus comprises its Form, its pure Actions, its Bonds, and its declared Effects.
            Agents can transplant this organ into another repository safely because its boundary seams and side-effects are completely explicit.
