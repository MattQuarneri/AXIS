Where does the actual View go in AXIS?

The Specification uses View → Facet / Intent as a conceptual bridge: the available ways to interact, and what someone means by an interaction. This is a lens on meaning, rather than a literal replacement for a screen.

For implementation, the Wrapper hosts the UI, the Adapter normalizes its input, and Impact performs DOM rendering. The DOM is a projection of Instance state. A Facet is a capability map; an Intent is a request with meaning.

02
The distinction underneath the names

A definition is different
from its realization.

AXIS calls these two perspectives Essence and Expression. “Static” and “dynamic” are a helpful entry point.

Essence / definition

What can be true?

A task has a title and a completion flag. A pure rule describes how completion works. A side-effect description says what should be saved.

  • Form: valid state shape and invariants
  • Action: deterministic transformation
  • Effect: an inert description of work
Expression / runtime

What is happening now?

This task is open at revision 0. A coordinator handles this request in this context. An executor attempts this particular save.

  • Instance: current values and revision
  • Manager: routing, workflow, commit
  • Impact: concrete effect execution

Definitions constrain behavior.
Behavior produces change.
Change becomes the next state.

“Static” describes a role, not a timestamp. An Action runs, but its rule remains a definition. An Effect can be created during execution, but it remains a description until Impact executes it. Definitions can evolve between compositions; they do not carry the live values of an Instance.

How purpose reaches the runtime

AXIS’s Cognitive Flow of Change traces how a higher-level purpose becomes behavior:

Values→Goals→Plans→Declaratives→Imperatives→Instructions→Actions→Behaviors→Change

For our example: value reliable collaboration → goal accurate project status → plan record completed tasks → rules and instructions → the completion behavior below. The chain explains the motivation. The seven pairs help place its implementation.

Try three pauses: after Action, the current Instance is still unchanged. After commit, the task can be complete while the external copy is still open. After Impact, the external result becomes a follow-up Intent that the Manager routes and commits.
Here we choose an optimistic local commit followed by an external save. That ordering is a workflow choice. AXIS makes the choice explicit; it does not make local state and remote IO one atomic transaction.


Why does a read need two passes?
Select Load a task. The first Action declares LOAD_TASK and changes no task state. Impact returns data as task.loaded. A second pure Action proposes that data, and the Manager validates and commits it.
A Link can resolve related state before an Action runs. Traversing an in-memory graph requires no IO; resolving a remote relationship still needs an Impact-backed loader. A Link names the relationship-resolution responsibility, rather than granting pure logic permission to fetch.


What the failures teach
Policy and validation
A Viewer has no complete delegate; an expired Token cannot authorize the request. A faulty Action may propose an empty title, or forget to update the project’s completed count. The Manager checks Form and Bond invariants before committing or handing the proposed save to Impact.
External failure
The failed-save experiment attempts the mock save twice (one retry), then returns a compensation Intent. The Manager restores the earlier values by committing a new revision. Compensation is a new transition, rather than deletion of history. Real distributed work also needs idempotency, version checks, and durable delivery where required.

How AXIS relates to the patterns you already use
Redux & functional cores
A Redux action object corresponds roughly to an AXIS Intent. A reducer corresponds to an AXIS Action. AXIS names the effect description and the executor separately, making the pure core easier to inspect and reuse.
DDD & CQRS
One Manager coordinates one consistency boundary. Bonds describe aggregate rules; Links resolve related state. Separate read and write Facets can express distinct capability surfaces.
Ports & adapters
Wrappers name the interaction boundaries; Adapters translate edge input into domain meaning. The same Action can serve browser, HTTP, or queue input without depending on their transport types.
Event sourcing & replay
Explicit Intents and deltas support audit and replay when recorded appropriately. Intent logging alone does not supply an authoritative event store, versioned rules, or safe re-execution of IO. Those remain deliberate implementation choices.

A feature recipe
  1. Describe the Intent in domain language.
  2. Define the state shape and invariants in a Form.
  3. Write the pure Action and assert its delta and Effects.
  4. Implement the needed Impact handlers.
  5. Register capabilities and commit rules with the owning Manager.
  6. Connect the Wrapper and Adapter at the edge.
Skip what the feature does not need. Keep native repository names. The roles tell you where responsibility lives.


Task boundary
Owns task & project state

Notification boundary
Owns delivery state
Accepts a normalized notification Intent. Applies its own policy and workflow. Declares delivery Effects.


The Manager stays narrow. Its Composer wires the parts; its Conductor routes requests, progresses workflow, and commits. Different roles for the same entity usually need different Facets. Different owned state or domain rules may need a different Manager.


A useful handoff to your next human or agent
A small architectural map should state the boundary’s owned state, accepted Intents, emitted Effects, returned outcomes, and policy scope. Then link those roles to the repository’s actual paths and symbols.
Feature: complete a task
Boundary: project board
State owner: tutorialManager (this demo's teaching state)
Pure logic: completeTask, applyTaskOutcome, labStep
Commit checks: validateTask, validateProject, validateBond
Edge normalization: normalizeInput
IO boundary: executeImpact (DOM and mock external results)

For an existing repository:
1. Trace an entry point and confirm responsibilities in source.
2. Name mixed roles honestly; retain native file names.
3. Record state ownership and every IO seam.
4. Carry contracts and tests with any reused capability.
5. Update the map when responsibility moves.
